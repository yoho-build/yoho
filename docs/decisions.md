# Decision log (grilling session 2026-10-08)

Small decisions that don't warrant an ADR. ADRs live in `docs/adr/`.

- Name: **yoho**. Binary `yoho`, config dir `.yoho/`, env prefix `YOHO_*`. `yoho.sh` unregistered (whois), `yoho.dev` taken.
- Config split: per-Service settings in compose `x-yoho`; where/how settings (Servers, Destinations, Builders, transport, secrets, provisioning, Backup Targets) in the Yoho file. Revisit later if needed.
- Config formats: YAML, TOML, JSON, JSONC, detected by content. JSON Schema generated from Go structs, published for editors and AI agents.
- Docs site built from the same repo (GitHub Pages).
- Provisioning v1: interactive `setup` that installs Docker + compose plugin and basics. Debian/Ubuntu first.
- One Server per Destination in v1. Roles later (see backlog).
- Builders: local, dedicated build Server, or the Destination's Server.
- Image transport: SSH layer push (unregistry-style) → `docker save | docker load` → registry.
- Proxy: kamal-proxy, ports configurable, see ADR 0004.
- Backups: ONCE contract (pre-backup hook or pause, post-restore). Targets: local, S3, B2, SFTP, rclone remotes (OneDrive, Google Drive). Archive formats incl. password-protected zip / 7z; password readable from a password manager.
- Agent skill ships in v1: "Yoho is like Kamal", built-in env vars, hook names. Coolify and Kamal migration is an agent-skill guide (Coolify CLI or SSH), not a command.
- Kamal-compatible hook names and secrets-file style, but under `.yoho/`.
- Scheduler: opt-in per Server, systemd timer per job, CLI-only by default (ADR 0003).
- Stateful Services pinned, `servers` always a list (ADR 0005).
- On-Server layout `/var/lib/yoho/<app>/<destination>/`, compose project `yoho-<app>-<destination>`, per-Server compiled compose, never `down -v`.
- Zero-downtime in one compose project: `--scale <svc>=2 --no-recreate` → kamal-proxy cutover → remove old.
- Secrets as files (ADR 0006); env_file fallback; `${VAR}` secret interpolation rejected by `yoho config check`; audit via ref + HMAC; `--reveal` TTY only.
- Backups (decided by Claude, user delegated): restic default (encrypted, dedup; S3/B2/SFTP/rclone); optional archive mode tar.gz / AES-256 zip / 7z, never ZipCrypto; passwords from password manager at schedule-install time, stored on Server.
- `yoho setup` v1 (delegated): interactive, shows each change before applying: Docker + compose plugin, deploy user + SSH key, ufw (SSH + Proxy ports), unattended-upgrades, optional swap/timezone/Proxy.
- License MIT (delegated). GitHub repo `yoho-build/yoho`; domain **yohobuild.com** (installer `curl -fsSL https://yohobuild.com | sh`, schema at `/schema/yoho.schema.json`, docs site).
- Generated secrets (Coolify-style): `x-yoho.generate`, created once on the Server, `yoho secrets backup` to password manager, included in encrypted Backups.
- Each Service gets only secrets it declares in `x-yoho.secrets`, with aliasing (container name ← secrets key). Common `.yoho/secrets` + `.yoho/secrets.<destination>`.
- Version = git SHA; a dirty tree appends `_uncommitted_<8 hex>` (content hash, with a warning); image tag = version; Release stores digests.
- The dirty suffix hashes uncommitted content, not a random id, so plan/apply converges: `yoho plan` after `yoho deploy` on the same uncommitted tree does not show a spurious image change (ADR 0008).
- Migrations: `x-yoho.release_command` in a one-off container from the new image before cutover; failure aborts. Pre-migration Backup off by default.
- Rollback: redeploy a previous Release (digests + compose), zero-downtime; volumes and migrations untouched, warned. Keep last 5 Releases per Server.
- Swarm (`docker stack deploy`) supported from the start, not compose-only. Details pending research.
- Reference projects to study: Coolify, Dokploy, OpenShip.
- Runtime: compose default, swarm opt-in, switch = downtime migration (ADR 0007). Swarm zero-downtime via start-first + VIP; `strict_drain` option.
- Swarm images: built locally, pushed to each node over SSH in parallel; registry optional.
- Secret refs: map `{NAME: KEY}` and Kamal-style list `["KEY", "NAME:KEY"]`.
- Fast health probes: when Yoho waits on a healthcheck (proxied compose cutover, or any Swarm service healthcheck) and the user set neither `start_period` nor `start_interval`, and the server Docker is 25 or newer, the compiled file sets `start_period: 60s` and `start_interval: 1s` so the first probes run every second while the container starts. User values are kept. Older engines omit both, because they reject `start_interval`.
- Swarm update width: when `deploy.update_config.parallelism` is unset, it defaults to the replica count (all new tasks start together, still start-first) and `monitor: 5s` unless set; the same defaults apply to `rollback_config`. `failure_action` stays `rollback`. One-at-a-time plus a 30s monitor was most of a two-replica deploy.
- App files: read-only bind sources and `configs:` files inside the App directory are shipped (tar over the Host's stdin) to `<app dir>/files/<content hash>/<name>`, not into `releases/<version>/`. A per-Version path would change every bind source on every deploy, so `yoho plan` would always report `volumes` changed and compose would recreate Stateful Services (ClickHouse, SeaweedFS) on each deploy. Content addressing keeps unchanged files at the same path; the Release record lists its hashes (`files`) so rollback and pruning treat them like secrets generations. Writable binds there are a `config check` error (named volumes hold state); cap 50 MB.
- Redeploying the Version `current` already points at (e.g. after rotating secrets) rewrites the same `releases/<version>/` files. A failed attempt restores the previous compose, plan and `release.json` instead of recording `failed` over them, so rollback and `yoho plan` keep the working config.
- Releases record `image_ids` (Service -> local image ID). Rollback re-tags Yoho-built images to the recorded ID; image pruning keeps recorded IDs. Third-party tags are never retagged (not Yoho's resource).
- Yoho-built image tags include the Destination: `<prefix>/<app>-<destination>-<service>:<version>` (was `<app>-<service>`), so staging and production builds of one Version on a shared Server no longer retag each other. Releases deployed before the change record their own refs and image IDs, so they still roll back. Registry users get new repository names.
- Pruning keeps the newest `retain_releases` successful Releases, `current`, and the newest failed record; a run of failed deploys cannot push rollback targets out. Swarm redeploys of the `current` Version restore the previous files and record on failure, like compose.
- A changed `x-yoho.release_command` is a plan change (service update, no restart) in compose and Swarm, so `apply` runs the new command even with an unchanged image. After kamal-proxy has switched the route, failing to stop or remove the old containers is a warning, not a failed Release.
- Scheduled Job unit and spec names join `<app>-<destination>-<job>` like project names. Existing units keep their names; `schedule install` refuses to overwrite a unit whose stored spec belongs to another App, Destination or job. Ownership collisions (compose, Proxy route, Scheduled Job) get their own CLI hint (rename the App or Destination).
- Compose project `yoho-<app>-<destination>` and route `<app>-<destination>-<service>` are ambiguous where `-` falls (App `foo-bar`/`prod` vs `foo`/`bar-prod`). Names are kept (renaming orphans deployed projects); deploy, rollback and plan refuse when the project's containers or a route's target containers carry another App's `yoho.app`/`yoho.destination` labels, and stale-route cleanup skips such routes.
- `deploy.replicas: 0` (or `scale: 0`) means zero containers, as in compose; a proxied Service scaled to zero has no route.
- Compose readiness prepares and gates Services in saved `depends_on` order (plain stop-first replacements or new Proxy candidates), and switches Proxy traffic only after every Service is ready; failed gates remove unswitched candidates with bounded cleanup while uncertain switches retain their candidates. Release-command prerequisites use the same readiness policy. Effective Docker healthchecks (including image-inherited checks) must be healthy; otherwise only running-process readiness is promised explicitly. Completion-only jobs are identified by an active consumer's `depends_on: condition: service_completed_successfully`, never by `restart: no`; an active completion dependency on a scaled-zero job fails preflight. Absent optional profile dependencies are pruned (legacy rollback recovers `required: false` from saved Compose), while missing required dependencies fail. Compose-run one-offs never count as replicas/candidates and are excluded from cutover cleanup. Zero replicas skip waiting. The plain deadline is at least 30s and covers effective health startup grace plus retries+1 interval/timeout budgets; Proxy deadlines remain explicit. Saved plans retain job classification, and rollback recovers it from retained Compose for older Releases. No automatic overlapping workers and no automatic undo of completed stop-first changes on readiness failure.
- Compose cutover goes by `depends_on` level (level 0 has no dependencies; otherwise one above the deepest dependency). The non-proxied Services of a level start with one `docker compose up -d --no-deps a b c` (still stop-first per Service) and their readiness gates run concurrently; proxied Services of the level then stage candidates one at a time, and the next level starts only after the whole level is ready. Release-command prerequisites are gated by level the same way. A failed batch `up` cannot name its Service, so all members are `attempted` and sampled like prerequisites; a failed gate names the first Service that failed and cancels the other gates of its level. Step output shows `starting level i/n` and `level i/n ready in`; per-Service readiness lines are kept, buffered per Service so they do not interleave. Sequential per-Service starts made an App with six independent Stateful Services wait the sum of their startups.
- Proxy route preflight rejects active desired hostname/path reservations already bound to a different route name, including an App's own obsolete Service route, before runtime operations or generated/env/Release files change. Compose and Swarm plan/deploy/rollback share the pinned kamal-proxy v0.10.2 rules; Swarm checks every Destination Server, and rollback checks the retained Release's routes rather than current local config. Hosts are literal and `--host` flags decode CSV; only equal hosts at equal normalized path prefixes conflict, so catch-all/specific, wildcard/specific, and distinct path routes can coexist. Proxy `list --json` displays both an empty catch-all host and a literal `*` as `*`; because that display loses the distinction, preflight fails closed for a different route requesting either possible binding and explains the ambiguity, without normalizing known desired literal `*` to catch-all. Query failures are not empty route lists, and same-name updates still require ownership checks. No automatic old-route deletion or forced rename: retain the Service name, or phase a rename with a different hostname first. Reusing the old hostname requires verifying the obsolete route belongs to the App and manually removing only that owned route on every affected Server (`docker exec yoho-proxy kamal-proxy remove <verified-owned-old-route>`) during a maintenance window; traffic is interrupted until the replacement is healthy. Never remove a foreign route. This is a read-only preflight, not a Server-wide reservation lock: an independent concurrent route change after the check can still cause a later Proxy refusal; existing uncertain-switch and candidate recovery rules remain unchanged.
- Backup filesystem trust: refuse unsafe existing ownership/modes/links instead of repairing configured parents. Root or deploy-user ownership and non-group/other-writable ancestors are required; owned sticky ancestors permit a private child, and root-owned filesystem aliases require physical-path validation. Run/check/restore use exclusive nonce staging with proof-of-creation markers; local archives publish complete files atomically without overwriting an existing ID. Outer extraction has only exclusive staged data writable, rejecting links/special entries; App-volume tar metadata/internal links remain intact. Format defaults, encryption, rclone semantics and fail-closed restore isolation/no-data-rollback are unchanged. No absolute protection against host root or an attacker using the deploy UID; local filesystem paths must be absolute and hard-link-capable. See the Backup filesystem trust policy in the site docs.
- Installer URL: the site root serves the docs HTML, so the installer is published at `https://yohobuild.com/install.sh` (copied from `scripts/install.sh` by the docs workflow, which also publishes the JSON Schemas under `/schema/`). The earlier `curl -fsSL https://yohobuild.com | sh` form does not work.
- Installer provenance stays opt-in: `install.sh` checks SHA-256 by default and verifies signed build provenance only with `YOHO_VERIFY_PROVENANCE=1` (via `gh attestation verify`, fail closed). Common `curl | sh` installers (rustup, bun, deno, uv) stop at checksums, and Homebrew's attestation check is opt-in too. Requiring `gh` and a login would break most first installs, and releases before attestations shipped cannot verify. A script fetched by `curl | sh` is itself unsigned, so a default check there adds little. The attestation API is reachable with plain curl, but verifying a Sigstore bundle (Fulcio chain, certificate claims, Rekor proofs, TUF root) in POSIX sh is too fragile, and no self-managed signing key is added beside the attestations. The Go Server-side downloader (`internal/dist`) now verifies provenance by default (next entry).
- Scheduled Job binary provenance is default-on and fail-closed: `internal/dist.Download` verifies the Release attestation for the binary's SHA-256 with `sigstore-go` (approved dependency) after the checksum, on every call including cache hits, under the same policy as `install.sh` (Actions OIDC issuer, `release.yml` at exactly `refs/tags/<version>`, repository URI and ref extensions, SLSA v1 predicate, SCT, Rekor entry and observer timestamp). The trusted root is Sigstore public-good via TUF from sigstore-go's embedded root, cached under `UserCacheDir/yoho/sigstore` with a one-day validity. Attestations come from the GitHub API (token sent when available); an inline bundle is preferred, otherwise `bundle_url` is fetched without Authorization and snappy-decoded in-package rather than adding another dependency. Bundles are not cached; fetching them is cheap and caching would not skip verification. There is no `YOHO_VERIFY_PROVENANCE` opt-out here: `--binary` and the cross-build from source already cover releases before v0.1.5 and offline Servers, and an environment switch would be a silent downgrade for unattended runs. Private-repo attestations signed by GitHub's own Sigstore instance are not supported.
- Per-Destination `app_dir`: the on-Server layout stays canonical. `<root>/apps/<app>/<destination>` remains the path every reader uses (path builders, Release records, compiled compose bind sources, image-retention globs, `schedule run`, older binaries) and becomes a Yoho-owned symlink to `app_dir`, rather than teaching `release.AppDir` about overrides. `app_dir` is owned completely (`.yoho-app.json` marker), must be outside `root` lexically and physically, and passes the Backup filesystem trust rules, now shared in `internal/safepath` with one narrow exception: the canonical App link when it is owned by the deploy user and points at a marked, trusted directory. Changing `app_dir` moves the directory in a confirmed `apply`/`deploy` (also `rollback`, `schedule install`) by same-filesystem rename only, never copy; coordination (Destination gate, App gate, `migrate.json` journal, `link.tmp`) lives in `<root>/appdirs/<app>/`, outside the moving tree. Every lock taker passes through the gate and refuses while a journal exists; migration and resume hold only the gates and refuse while the tree holds `lock/` or `source.run-*`; image pruning is skipped while any Destination of the App is moving. Cross-filesystem moves are manual. See `docs/dev/plan-app-dir.md`.

## Scoped access P1 (ADR 0011)

- Gate wire format: one JSON request line (`protocol`, `app`, `destination`, `verb`, `args`; 16 MiB max), then for `deploy` a chunked payload (4-byte big-endian length + bytes, zero length ends it), so stdin stays open and its EOF tells the Gate the client left (it stops `logs -f`; a deploy or rollback runs to completion). Responses are NDJSON frames on stdout: `out` text, then one `result` or `error` (`message`, `hint`, `code`). Exit 0 ok, 1 failed, 2 denied.
- Forced command `restrict,command="sudo -n /usr/local/bin/yoho gate --member M --key SHA256:…"`; sudoers `yoho-gate ALL=(root) NOPASSWD: /usr/local/bin/yoho gate *` with `!use_pty`, `env_reset`, a fixed `secure_path` and `env_keep = SSH_CONNECTION`. The Yoho root is read from root-owned `/etc/yoho/gate.json`, never argv (an old `--root` flag is ignored). The Gate ignores SIGPIPE and SIGHUP so a vanished client cannot kill a deploy mid-way; verbs run in their own process group, killed whole when a `logs -f` client leaves. The fingerprint comes from the forced command, so no sshd change (`ExposeAuthInfo`) is needed.
- The Gate runs as root only to read the access directory and switch users: every verb runs as the owner of the App directory (credentials + supplementary groups via `remote.Local.As`), so files stay the deploy user's and operator deploys keep working.
- Deploy sends the resolved compose project (`composefile.Resolved`: env_file/label_file inlined), not `plan.Deploy` JSON; the Gate reloads it with compose-go without interpolation, include, extends or env files, applies the policy, then builds `plan.Deploy` itself and calls `deploy.Compose`. Member Hooks run locally; the Gate passes no Hook.
- Proxy, Registry, retention and allowed Proxy hostnames come from `access/settings.json`, written by `yoho access secrets push`, never from the Member's Yoho file: the Proxy is shared by every App.
- Secrets: the Gate reads the generation named in `<app dir>/access-secrets` (written by the push, owned by the deploy user so pruning keeps it), never the newest one, and delivers only the names each Service declares; missing names fail with a hint to push. Image archives are spooled to `access/.gate-upload-*` under a per-App flock (stale spools swept), bounded by `limits.max_upload_bytes` and `limits.upload_timeout_seconds`, parsed strictly (regular files and directories under canonical names, no duplicates, no bare OCI tag names), refused if any tag is not a built image of this deploy, then `docker load`ed.
- Isolation: scoped Apps get their own Proxy network `yoho-<app>-<dest>-proxy` (`plan.Scoped.ProxyNetwork`, labeled `yoho.proxy.attach=1`, which the Proxy rejoins after a recreate); external networks are refused. The Gate drops `NET_RAW`, defaults `pids_limit`, sizes unsized tmpfs, and refuses Yoho-built images it did not build, unlisted host ports, oversized shm/tmpfs/ulimits/pids, empty projects (unless `limits.allow_empty`), shared compose project or image names (from other App Destinations' Releases), foreign volumes/networks/image tags (labels), and local images without a matching repo digest. Read verbs refuse a project with foreign containers and pin container IDs. Built images carry `yoho.destination`.
- Images and resources: the Gate sets `pull_policy: never` and pulls non-built images itself, anonymously (empty `DOCKER_CONFIG`) unless under `limits.registries`, so Server credentials never fetch private images for Members. References are normalized (lowercase registry host, Docker Hub and `library/` defaults) before every prefix comparison. `network_mode` is only `none` or unset (`bridge`/`default` is docker0). Memory, CPU, replica and container-count limits default to 2 GiB, 2 CPUs, 4 and 16; disk is not capped.
- Rollback: the Gate records each Release it deploys in `access/vetted/<version>.json` (Member compose, built Services, compiled compose sha) and `plan.Scoped.Vet` re-checks it inside the lock against today's policy, the hardened values of the compiled compose against today's limits (`Policy.CheckCompiled`), and the per-App network; operator Releases are refused. Short versions resolve in the Gate.
- Locks: Gate locks carry pid and boot id; a later Gate run clears a lock whose Gate is gone (`gate.ClearStaleLock`), checking and removing under `access/stale-lock.flock` and re-reading the record before removal. Members see a lock message without Server paths.
- `YOHO_ACCESS=operator|scoped` overrides a Destination's `access`, so one shared Yoho file works for the operator and Members.
