# v0.7.1

A patch release on top of v0.7.0 with one fix for scoped access: an App's own `cloudflared` Service may list the `yoho` network, so the same compose file works for the operator and for Members. Nothing changes for operator deploys.

## Upgrade notes

- **Gate (`yoho access install`): yes, to use the fix.** The new rule lives in the Gate's policy (`internal/gate/policy.go`) and in the compile step the Gate runs (`internal/deploy/compile.go`). Until the operator runs `yoho access install -d DESTINATION` with v0.7.1, the Server's v0.7.0 Gate keeps refusing a compose that lists `yoho` (see below). Everything else works with a v0.7.0 Gate; the Gate protocol did not change, so a v0.7.0 CLI and a v0.7.1 Gate work together.
- **Gate settings (`yoho access secrets push`): no.** `settings.json` and the pushed secrets keep their shape. The Gate accepts `yoho` only for an App whose settings already allow at least one Proxy hostname (`routes`, written by an earlier push from the Yoho file's `x-yoho.proxy.hosts`). An App that has never had a proxied Service gets `the operator allowed no Proxy hostname for this App, so it may not join the Proxy network`; the operator gives a Service a Proxy host and runs `yoho access secrets push`, as before for any new hostname.
- **Older Gate and new compose: a v0.7.0 Gate refuses it.** A compose with `networks: {yoho: {external: true}}` sent to a v0.7.0 Gate fails with `the Gate refused this deploy: network yoho: external network "yoho" is not allowed (scoped Apps get their own network to the Proxy; shared networks reach other Apps)`. Run `yoho access install` with v0.7.1. Nothing a v0.7.0 Gate accepted is refused now: a v0.7.0 Gate could not deploy any Service on `yoho` (the external network was refused, and the compile refuses a non-external one), so the new rule that Service entries on `yoho` must be bare (no aliases, addresses, priority or driver options) affects no existing App.
- **Running containers: no restarts from the upgrade.** Upgrading the CLI or running `yoho access install` touches no container. The compile change applies only to a scoped deploy whose compose lists `yoho: {external: true}`, which v0.7.0 refused, so the next deploy of an existing App compiles the same file and recreates nothing because of this release. When a Member first adds `yoho` to the `cloudflared` Service, that deploy recreates `cloudflared` (its networks change), creates `yoho-<app>-<destination>-proxy` if needed and connects the Proxy to it with `docker network connect`, which does not restart the Proxy.
- **Proxy: unchanged.** The default Proxy image and its configuration are the same as in v0.7.0.

## Changes

- Scoped access: a Service may list `networks: [default, yoho]` with `networks: {yoho: {external: true}}` (the in-App `cloudflared` of `examples/basic`). The Gate maps it to the App's own Proxy network `yoho-<app>-<destination>-proxy`, never the shared `yoho` network, so the connector reaches `http://yoho-proxy:80` and no other App. Allowed only when the operator allowed a Proxy hostname for the App, with no `driver` or `driver_opts` on the network, and only bare Service entries on it, `pre_start` containers included.
- `yoho rollback` through the Gate re-checks such Releases with the same rule.
- The reusable workflow `.github/workflows/deploy.yml` and its `setup-yoho` step default to v0.7.1.
- Docs: [Team access](../site/team-access.md) (external networks, other Apps on the Server) and [Cloudflare Tunnel](../site/cloudflare-tunnel.md) describe the scoped case.
