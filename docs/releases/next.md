## Upgrade notes

- **Gate (`yoho access install`): yes, for scoped `yoho plan` and for `x-yoho.check`.** The Gate gains a read-only `plan` verb (#65) and learns `x-yoho.check` (#68). Until the operator runs `yoho access install -d DESTINATION` with this release, a Member's `yoho plan` stops with `the Server's Gate cannot plan`, and a scoped deploy of a compose with `x-yoho.check` is refused (next answer); both errors carry the hint to update the Gate. Deploys and rollbacks of composes without a check, and the read verbs, work with the previous Gate as before. `yoho tunnel route` (#67) is operator-only and needs nothing on the Gate.
- **Gate settings (`yoho access secrets push`): no.** `settings.json`, the pushed secrets and `members.yml` keep their shape. `plan` uses the Member's existing `deploy` grant; no grant needs to change.
- **Older Gate and new compose: yes, `x-yoho.check`.** A Gate of v0.7.1 or older decodes `x-yoho` strictly and refuses a compose with `check` with `unknown key "check"`; the new CLI adds that the Gate is older than the CLI and to run `yoho access install -d DESTINATION`. Composes without a check work with old Gates. The `plan` verb sends the same compose a deploy sends.
- **Running containers: no restarts.** Upgrading the CLI or the Gate touches no container. Adding or changing a check restarts nothing: `yoho plan` shows `update` with `check changed`, and the next deploy runs the new check against the running containers. The operator plan only words its reasons differently (see Changes); what an operator or Gate deploy recreates is unchanged.
- **Proxy: unchanged.** The Proxy image and its configuration stay the same.
- **Checks through SSH.** An operator deploy and `yoho app ps` open the check connections through the SSH connection (`ssh -W`), so the Server's sshd must allow TCP forwarding (`AllowTcpForwarding yes` or `local`, the OpenSSH default); a Gate deploy dials directly on the Server.
- **A failing check fails the deploy** and leaves the new containers running (non-Proxy Services are replaced stop-first); the hint names `yoho rollback <version>`. A rollback does not revert volumes or migrations.
- **Rollback warning with a Tunnel API token.** With both `proxy.tunnel.token_secret` and an API token secret configured, `yoho rollback` warns (never fails) when a hostname of the target Release still bypasses the Proxy. Nothing changes for configs without an API token.

## Changes

- `yoho plan` with scoped access runs through the Gate (#65). The Gate vets and hardens the compose exactly as a scoped deploy does and compares it with what runs, so a plan right after a Gate deploy shows no changes, instead of every non-proxied Service as `replace` with `config changed: cap_drop, cpus, mem_limit, pids_limit, pull_policy`. It pulls, locks and writes nothing, and needs the `deploy` grant.
- An operator `yoho plan` against a Release that the Gate deployed keeps showing those Services as `replace`, because an operator deploy really recreates them without the Gate's limits, but now says so: `Gate hardening removed by an operator deploy: …`, with a warning that points to `YOHO_ACCESS=scoped yoho plan`.
- New: `yoho tunnel route --hostname HOST --to proxy` (#67) points one ingress rule of a remotely managed Cloudflare Tunnel at the Proxy. It checks the route through the Proxy first and that the rule is the one Cloudflare uses for the check path, prints the old rule and the exact undo command, switches only that rule in the configuration as it is then (refusing when the rule changed meanwhile), checks `https://HOST<check path>` (2xx, or NNN for `--to http_status:NNN`; other non-HTTP targets are not checked), and puts the old rule back when that check fails. It needs `proxy.tunnel.api_token_secret` (a Cloudflare API token with Account > Cloudflare Tunnel > Edit); an existing `migrate.tunnel.api_token_secret` also works. `yoho tunnel up` now suggests `yoho tunnel route`.
- New: `x-yoho.check` (#68) gives a Service the Proxy does not route (a WebSocket server, a broker behind a tunnel) a `tcp`, `http` or `websocket` check that a deploy and a rollback run after the containers are ready (default timeout 30s, at most 10m). `yoho app ps` adds a `CHECK` column, and `yoho tui` and `yoho ui` show the result per container. Refused with `x-yoho.proxy`, on one-shot jobs, with `network_mode: none` and on runtime `swarm`.
- `yoho plan` no longer lists `x-yoho` as a changed compose key. A change that lives only in `x-yoho` (a check, a `release_command`) used to show the Service as `replace` with `config changed: x-yoho`, although Docker leaves `x-*` keys out of its config hash and recreates nothing; it now shows its own reason (`check changed`, `release_command changed`, `proxy settings changed`).
- Release notes with upgrade answers live in `docs/releases/` (#66); the release workflow publishes them and refuses a stable tag without them.
