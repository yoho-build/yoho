# v0.9.0

## Upgrade notes

- **Gate (`yoho access install`): recommended, not required.** A v0.8.2 Gate keeps serving Members, and the Gate protocol and verb arguments are unchanged. The new Gate adds: an `accepted` frame, so a Member's CLI reports a dropped connection after the Gate accepted the deploy as outcome `unknown` (exit 14) instead of `failed` (exit 1); an operation record per Gate deploy or rollback (`yoho status --operation ID`, Operators only) with `partial` outcomes and changed/unchanged Service lists; `operation_id` in `audit.log` and in the Release; Services kept down by `yoho app stop` stay down through Member deploys and rollbacks; `x-yoho.proxy.ssl` is accepted; and the policy refuses `x-yoho.tags` by name. Until the Gate is updated, a Member deploy or rollback through it starts a Service an Operator stopped with `yoho app stop`, writes no operation record, and refuses `x-yoho.proxy.ssl` (see below). Run `yoho access install -d DESTINATION` with this release.
- **Gate settings (`yoho access secrets push`): no.** `settings.json`, the pushed secrets generation and `members.yml` keep their shape, and no new setting comes from the Yoho file. You do not need to push again.
- **Older Gate and new compose: `x-yoho.proxy.ssl` is refused.** A v0.8.2 Gate reads `x-yoho` strictly, so a Member who sends the new `x-yoho.proxy.ssl` key gets `compose: service "web": x-yoho: unknown key "proxy.ssl"`. The other new compose key, `x-yoho.tags`, never reaches a Gate: the CLI refuses it for scoped access (`x-yoho.tags requires operator access; the Gate refuses per-Server environment`), and the new Gate refuses it with the same message. Roles, Connections, `network` and Server `tags` are Yoho file keys and require operator access. An older CLI refuses every new Yoho file key (`network`, `servers.<name>.tags`, `servers.<name>.endpoint`, `destinations.<name>.roles`, `destinations.<name>.connections`, `previews.max_active`) as an unknown key, so upgrade every operator and Member before you use them.
- **Running containers: no restarts.** Upgrading the CLI or the Gate touches no container. A Destination that uses none of the new keys renders the same Compose file, so the next deploy recreates no Service because of this release. Adding `x-yoho.tags` changes the environment of the matching Services on the next deploy, which recreates them as for any environment change.
- **Proxy: unchanged.** The default image stays `basecamp/kamal-proxy:v0.10.3` and its configuration is the same, so a Proxy already on v0.10.3 is not recreated.
- **`yoho setup` restarts Docker on an empty Server.** Setup now enables Docker's containerd image store (the `docker pussh` layer-diff path) by default, but only when Docker is absent or `docker ps` finds no running containers; enabling it restarts Docker. A Server with running containers, or whose state cannot be read, is skipped with a hint to run `yoho setup --containerd-image-store` in a maintenance window. Pass `--no-containerd-image-store` to opt out.
- **Exit codes of mutating commands.** Failures that exited 1 now use dedicated codes: 10 configuration or validation error, 11 Destination lock held, 12 cannot connect before the mutation, 13 partial outcome (including `jobs_failed`), 14 outcome unknown after the mutation began, 15 stale, expired or invalid saved plan. `yoho plan --detailed-exitcode`, `yoho config check` and `yoho app exec` keep their codes. Update scripts that test for exit 1. Every `--json` event now carries `schema_version: 1` (`yoho schema --events` prints the schema).
- **New on-Server files.** Under the App directory: `operations/<id>.json` (one record per operator mutation or Gate rollout, the newest 50 kept), `stopped.json` and `stopped.compose.yaml` (Services kept down by `yoho app stop`), and `promotions/<connection>.json` (the `yoho db promote` journal). `release.json` gains optional `operation_id`, `roles`, `connections` and `generated_owners` fields; older CLIs ignore them, so rollback across versions still works. Preview markers (`preview.json`) gain `created_at` and `last_deployed_at`; previews created before this release show `unknown` age, and `yoho preview prune --older-than` skips them unless `--include-unknown-age`. `yoho mesh up` writes `/etc/wireguard/yoho0.conf` and Yoho-tagged firewall rules only when `network.mesh: wireguard` is set.
- **Do not deploy a stopped Service with an older CLI or Gate.** Only this release reads `stopped.json`. A v0.8.2 CLI or Gate deploying the Destination starts a Service kept down by `yoho app stop`.
- **Workflow callers:** `deploy.yml` and `yoho-preview.yml` install Yoho v0.9.0 by default and pin `setup-yoho` to v0.9.0.

## Changes

- **Roles** (ADR 0017, 0019): `destinations.<name>.roles` spreads an App's Services over several Servers on the Compose runtime, without Swarm. `connections` publish a provider's port only on the Server's private address, with Yoho-owned firewall chains, `YOHO_CONNECTION_<NAME>_HOST`/`_PORT` and `extra_hosts` so Service names keep working across Servers. `yoho service move SERVICE --to SERVER` moves a Stateful Service with a fresh Backup and a stop-first cutover. `x-yoho.proxy.ssl: false` serves Roles behind an external TLS load balancer. Swarm is frozen. See `docs/site/roles.md`.
- **Per-Server tags and environment** (ADR 0020): `servers.<name>.tags` plus `x-yoho.tags.<tag or Server>.env` give a Service a different environment on each Server (Compose environment, then tags in order, then the Server name). Compose runtime and operator access only.
- **Instance Connections** (ADR 0020): `instances: true` on a Connection lets a non-proxied provider with one container per Server run on several Servers; consumers reach each copy as `<server>.m.<service>` and `<server>.m.<service>.<app>.yoho.internal`.
- **WireGuard mesh** (ADR 0018, #86): `network.mesh: wireguard` with `yoho mesh up`, `mesh status`, `mesh rotate-keys` and `mesh down`, with no Yoho daemon. A Server with `endpoint: none` joins outbound-only through a hub. `yoho plan` works on a Roles Destination before the first `mesh up`; rerunning `mesh up` on the hub no longer fails on the UFW route rule.
- **`yoho app stop SERVICE` and `yoho app start SERVICE`** (ADR 0021): stop removes a Service's containers and keeps it down through deploy, apply and rollback; `yoho plan` and `yoho app ps` show it as stopped; only `app start` brings it back. Volumes are never touched.
- **`yoho db promote [CONNECTION]`** (ADR 0021): promotes a streaming Postgres standby after you point the Connection at it. It checks streaming and lag, fences the old primary with `app stop`, waits for replay, runs `pg_promote()` and applies. Every step is journaled and resumable.
- **Tested replication recipes:** `examples/postgres-replication` (primary/standby, fenced promotion) and `examples/mysql-replication` (MariaDB 11.4 primary and GTID replica), each walked end to end in CI. See `docs/site/postgres-replication.md` and `docs/site/mysql-replication.md`.
- **Saved plans and outcomes** (#75, #77): `yoho plan --out FILE [--ttl 1h]` and `yoho apply --plan FILE` apply exactly the reviewed plan, rechecked under the Destination lock. Every mutating command prints an operation ID, ends with an outcome event (`success`, `partial`, `failed`, `unknown`) and a dedicated exit code; `yoho status --operation ID` reads the outcome later.
- **`yoho doctor`** (#84): one read-only check of whether a Destination is production-safe: config and Backup coverage, Backup freshness and the last restore drill, firewall and public ports, free disk, Proxy state, pending secret rotations and image transport path.
- **Previews** (#78): `yoho preview prune --older-than D --keep N`, `previews.max_active`, and `--pr`/`--branch` metadata on `preview up`. `yoho-preview.yml` has an opt-in scheduled prune job.
- **Image transport** (#79): every deploy says why it takes the full-archive path instead of `docker pussh`, and `yoho setup` enables the containerd image store on Servers without running containers. A scoped deploy with `transport.mode: pussh` is refused with a hint instead of falling back silently.
- **Recovery and fault tests** (#76, #80): CI restores an App on a blank Server and deploys under SSH loss, a full disk and a Docker restart. `yoho backup restore --report` prints the recovery point and restore duration. A failed lock write on a full disk no longer leaves a stuck lock, and a signaled SSH session is classified as outcome `unknown`.
- Backup staging cleanup (`yoho backup restore --cleanup` and stale-staging checks) works on a macOS Server or a local host: it reads directory times with BSD `stat -f %m` when GNU `stat -c %Y` is missing. Before, every staging directory was skipped.
