# Grok grok-4.7 consult

## Q1. Roles without a v1 break

Keep v1 as one Server per Destination running the whole App, and make that the implicit Role `all`. Freeze a shape that later Roles fill in: `servers` is always a list, `roles` is optional, and a missing `roles` key means every Service on every Server of that Destination. A stateful Service is a singleton pin: it may belong to only one Role, and that Role may name only one Server.

```yaml
# .yoho/yoho.yml
app: leet-mgr
destinations:
  production:
    servers: [web-1.example]          # v1: exactly one
    # later:
    # servers: [web-1.example, web-2.example, db.example]
    # roles:
    #   web:  { services: [web, worker], servers: [web-1.example, web-2.example] }
    #   data: { services: [postgres, redis], servers: [db.example] }
```

```yaml
# compose.yaml — per-Service settings stay in x-yoho
services:
  postgres:
    x-yoho:
      stateful: true
      endpoint: postgres.internal.example   # required once dependents run elsewhere
      backup: { dump: "pg_dump -U app -d app", volumes: [pgdata] }
  web:
    x-yoho: { proxy: true, health: /up }
```

On each Server:

```text
/var/lib/yoho/<app>/<destination>/
  compose.source.yml      # canonical project, same bytes on every Server
  compose.compiled.yml    # this Server's Services only; Yoho overwrites it
  runtime.env             # 0600 root:root
  secrets/                # 0600 files for compose secrets:
  releases/<ulid>.json    # digests, role, server, secret fingerprints
```

Project name is `yoho-<app>-<destination>`. v1 writes `role: all` and the Server name into the release record so later Yoho can see what ran where.

Compile a per-Server compose file. `docker compose up web` would still start `depends_on: postgres` and create a second database. The compiled file omits unplaced Services and drops those `depends_on` entries. Compose profiles stay a user feature. Each deploy runs:

```bash
docker compose -f /var/lib/yoho/leet-mgr/production/compose.compiled.yml \
  -p yoho-leet-mgr-production up -d --remove-orphans web worker
```

`--remove-orphans` only sees this Server's compiled project. Leaving a Server is `stop` and `rm` of that Service. Yoho never `down -v` as part of a Role move.

Cross-Server discovery is a hostname, not a Yoho network. On the Server that holds `postgres`, Compose DNS name `postgres` works. On a web Server it does not exist. Dependents get `DATABASE_HOST` from the pinned Service's `x-yoho.endpoint` (Tailscale, VPC, or private DNS). The user brings that reachability. Identical web Servers each run their own Proxy; spreading traffic across them is DNS or Tunnel replicas.

A named volume with no `stateful` and no `replicated: true` (cache, safe to duplicate) is a hard error once a Destination has more than one Server. `replicated: true` is the explicit opt-in for disposable per-Server disk.

Backups run on the Server that pins the stateful Service. The timer on web Servers skips that job. Restore targets the current pin. If the pin Server changed, restore is allowed only with an empty volume and an explicit move. Order: backup, stop, restore on the new Server, then start. Starting first creates an empty database that looks healthy.

Risks: a bad compiled file can drop a dependency and boot the App against the wrong host. A hand-edited compiled file is overwritten next deploy. `remove-orphans` on a shared project name deletes another App's containers; the `yoho-<app>-<destination>` name is load-bearing. Moving Postgres without the empty-volume check splits writes. Endpoint drift leaves web Servers on a stale hostname until the next deploy.

## Q2. Secrets

Resolve secrets on the operator machine at deploy time. Store the values on the Server. Scheduled work reads those files and does not call 1Password at 03:00.

```text
.yoho/secrets                 # dotenv, $(op read …), $(bw …), $(bws …), $(cmd)
.yoho/secrets.<destination>   # overrides; both gitignored
```

Build secrets stay on the Builder and go to buildx `--secret` / compose `build.secrets`. They are not uploaded and are not in the image. Runtime values are uploaded to:

```text
/var/lib/yoho/<app>/<destination>/runtime.env          # 0600, env_file
/var/lib/yoho/<app>/<destination>/secrets/<name>       # 0600, compose secrets: file
```

Both survive reboot. The compiled compose points `env_file` and `secrets:` at those paths and contains no secret values. Committed compose must not interpolate runtime secrets with `${VAR}`: Compose resolves that on the client, so values land in `docker compose config`, shell history, and the compiled file. Non-secret interpolation (image tag, public port) uses a separate env file.

Default the backup-archive password and database passwords to `secrets:` files mounted only on the Services that need them. Use `env_file` for the rest, matching current apps. `docker inspect` shows env; it does not show file-secret contents. Directory mode `0700`, owner root. `setup` must not leave a 0644 `.env` in the rsync'd app dir.

A 1Password service account or `bws` token on the Server is a larger blast radius (it can read whatever the token can read, and 03:00 backups fail when the manager is down). That path is opt-in for values that must rotate without a deploy. The token file is 0600 and separate from the App's runtime env.

Each release records secret refs plus a value fingerprint, never the value:

```json
{"secrets": {"DATABASE_URL": {"ref": "op://prod/leet/db-url", "sha256_8": "9f3a12bc"}}}
```

Rotation is `yoho secrets push`, which rewrites the files and recreates Services that consume them. Recreating Postgres to rotate its password is a planned step with a hook, not a side effect of an unrelated deploy. Logs from SSH and Compose pass through a redactor seeded with the resolved values. `yoho secrets` prints names and refs. `yoho secrets print --reveal` writes only to a TTY and refuses a pipe.

Risks: fingerprints confirm which version was deployed; they do not prove the container picked it up after a failed recreate. Env secrets remain visible to anyone who can reach the Docker socket. A redactor misses values that another tool base64-encodes. `secrets push` onto a live database password can lock the App out before the database role is altered.

## Q3. One scheduler per Server, opt-in

Use a systemd timer that runs the `yoho` binary once per Server. Skip a sidecar per Service, a sidecar inside the App project, and a default resident daemon.

ADR 0003 holds: `yoho deploy` over SSH uses Docker only. `yoho setup` installs the timer only when `schedule: true` or the operator runs `yoho schedule install`.

```text
/usr/local/bin/yoho
/etc/systemd/system/yoho-schedule.timer      # OnCalendar=*:0/5, or 03:00 for backups
/etc/systemd/system/yoho-schedule.service    # oneshot: yoho schedule run
/var/lib/yoho/schedule-state.json
```

The App project is the wrong place for this. `compose down`, rollback, or a failed deploy would stop the job that is backing that App up. A per-Service sidecar would multiply Docker-socket holders and still cannot see App-level quiesce. One system container is the fallback where installing a binary is unacceptable; it is still one per Server, still opt-in, and still root-equivalent if it mounts the socket.

The timer runs Backups on Servers that pin a stateful Service: pre-backup Hook, otherwise pause, dump, volume archive, then the Backup Target. The archive password comes from that Server's secrets file.

The backlog dashboard binds to `127.0.0.1` or a Tailscale address, with a bearer token in `/var/lib/yoho/api.token` mode 0600. It stays off the public Proxy. Split the processes: the timer unit may use the Docker socket; the API unit may only read status JSON the timer writes. Socket plus HTTP in one container is the ONCE backup-directory class of bug.

Risks: a root timer with the socket is a second root on the box. A stuck pause during backup is an outage; the timer needs a deadline and an unpause in `Finally`. Two operators deploying while the timer pauses the database will fight unless the Destination lock covers both. An API that later shares the socket turns a dashboard bug into host control.
