# Codex gpt-6.1-sol consult (session 01a11bbc-6c57-70e3-9aaf-e82af2edcfe1)

## Q1 — Stable placement, explicit state ownership

**Recommendation:** use named Servers and a Server list per Destination immediately, while v1 validates exactly one Server; reserve additive Roles for later, with omitted Roles meaning the whole App runs on the Destination’s sole Server; keep Service properties in compose `x-yoho` and placement in the Yoho file:
```yaml
# yoho.yaml — v1
app: shop
servers:
  primary: {ssh: deploy@server-a, private_address: 10.20.0.1}
destinations:
  production:
    servers: [primary]
    state_owners: {db: primary}
```
```yaml
# compose.yaml
services:
  db:
    image: postgres:17
    volumes: [pgdata:/var/lib/postgresql/data]
    x-yoho:
      stateful: true
      singleton: true
```
```yaml
# Later, additive Destination configuration
servers: [primary, web2]
roles:
  data: {services: [db], servers: [primary]}
  web: {services: [web, worker], servers: [primary, web2]}
state_owners: {db: primary}
```
**Why:** Roles describe placement, not a replacement for Compose Services; compile the canonical Compose model into complete per-Server manifests rather than relying on profiles or `up <services>`, whose dependency behavior can accidentally start another database; validate dependency edges, reject overlapping placements, and require explicit external endpoints for dependencies absent from that Server; persist under `/var/lib/yoho/apps/shop/production/servers/primary/`, with immutable `releases/<id>/`, `current`, and a stable `state/` inventory; use a stable state Compose project and explicit volume names independent of release IDs, with separate release projects for stateless candidates, so `--remove-orphans` cannot remove the database and blue/green deploys never duplicate it; reserve volume deletion for a separately confirmed destructive command; later cross-Server connections should use private networking or operator-managed WireGuard/Tailscale, stable private DNS, scoped firewall rules, and application credentials, never an assumption that Compose DNS spans Servers; deploy using `yoho deploy -d production`, health-gate and drain each stateless Service through the shared Proxy, and retain old releases without pretending image rollback reverses database migrations; **risks:** reject multi-Server placement of any Service with named volumes, writable bind mounts, or declared state unless it has an explicit single owner or declared externally managed storage semantics, treating ambiguous storage conservatively and retaining the singleton constraint even with external volumes; owner changes must be explicit migrations, not ordinary deploys; run Backups on the owner under an App-wide operation lock, quiesce writers on every Server or use a documented database-consistent dump protocol, record owner/volume identity, schema and image versions, secret references and encryption-key version, and restore into fresh storage for validation before switching, with cross-Server restore fencing the old owner first to prevent split-brain.

## Q2 — Resolve locally; persist only necessary Server secrets

**Recommendation:** expose a common provider interface for `op`, `bw`, `bws`, and arbitrary commands, resolving deployment secrets on the operator’s machine and transferring them through SSH without command-line values; support explicitly trusted, shell-evaluated `.yoho/secrets` plus `.yoho/secrets.production`, with Destination keys overriding common keys, but never evaluate these during ordinary config inspection:
```yaml
secrets:
  providers:
    vault: {type: op}
    custom: {type: command, argv: [my-secret-helper]}
  values:
    DB_PASSWORD: {provider: vault, ref: 'op://Production/Postgres/password'}
    BACKUP_PASSWORD: {provider: vault, ref: 'op://Production/Backups/password'}
  build: [PACKAGE_TOKEN]
  runtime:
    db: {files: [DB_PASSWORD]}
    web: {env: [DB_PASSWORD]}
  scheduled: [BACKUP_PASSWORD]
```
**Why:** default to durable, root-owned `0700` secret directories and atomically written `0600` versioned files under `/var/lib/yoho/apps/shop/production/secrets/<generation>/`, surviving reboot without a laptop or mandatory vault availability; use Compose file-backed `secrets:` and `/run/secrets/...` wherever applications support them, falling back to Service-specific `env_file` files only where needed, with an explicit readability strategy for non-root container users rather than assuming Compose file-backed secret UID/mode options work; non-Swarm Compose secrets are bind-mounted files, not encrypted Docker secrets, while tmpfs alone loses data on reboot and should be an optional mode requiring unattended rehydration; keep runtime values out of Compose interpolation by default, because `${VAR}` can materialize credentials in rendered configuration, and remember `env_file` does not supply Compose interpolation; when interpolation is explicitly necessary, render only in protected temporary storage and never persist or log resolved manifests; send build credentials exclusively through BuildKit/buildx secret mounts, never build arguments or image environment, including secure delivery to a remote Builder and cleanup, while documenting that a Dockerfile can still deliberately copy mounted secrets into layers; scheduled Backups should default to a locally provisioned encryption password and narrowly scoped Backup Target credentials, needing no password-manager machine token, with optional per-job vault fetching through a scoped 1Password service account or `bws` token and a declared failure policy; **risks:** root, Docker administrators, and compromised applications can access secrets, environment secrets are additionally visible through container inspection, disk persistence requires encrypted storage where physical compromise matters, and server-held vault tokens increase blast radius; rotate by resolving and staging a new generation, coordinating database credential changes with consumers, recreating containers or health-gating stateless replacements, and retiring old credentials only after the rollback window, retaining old Backup decryption keys for the archive retention period; audit provider references and version identifiers where available plus an opaque deployment generation, never plaintext or plain hashes of low-entropy secrets; redact known values, suppress provider stdout/stderr and shell tracing, avoid wholesale secret injection into Hooks, and make `yoho secrets print` show references/status unless explicitly authorized with an interactive reveal or explicit sensitive-output flag.

## Q3 — Opt-in systemd timers, not per-Service sidecars

**Recommendation:** install a pinned Server-side Yoho binary and systemd timers only through an explicit scheduling command, keeping normal deploys agentless as ADR 0003 requires:
```yaml
# yoho.yaml
scheduler:
  backend: systemd
backups:
  nightly:
    destination: production
    services: [db]
    schedule: '*-*-* 03:00:00 UTC'
    target: offsite
    password_secret: BACKUP_PASSWORD
```
Use `yoho schedule install -d production` to create `/usr/local/libexec/yoho`, a root-owned job specification under `/etc/yoho/jobs/shop-production-nightly.yaml`, and `yoho-backup-shop-production-nightly.service` plus its timer under `/etc/systemd/system/`, invoking a bounded local command such as `yoho backup run --job /etc/yoho/jobs/shop-production-nightly.yaml`; **why:** one timer per Backup job, rather than one sidecar per Service, survives App replacement, supports cross-Service Backup coordination, produces system journal logs, and leaves no resident process between jobs, with the same operation lock used by SSH deploys/restores and explicit timezone, missed-run, timeout, retry, and failure-notification behavior; expose a future dashboard through one separately opted-in agent per Server, outside App Compose projects, with narrowly defined read-only operations, outbound telemetry preferred, and a local socket or loopback listener reached through SSH/Tailscale or an authenticated Proxy/Tunnel, never a public unauthenticated Docker-management API; **risks:** Docker socket access is effectively root even when the socket is mounted read-only, so privileged Backup runners must consume root-owned specifications, restrict writable paths, reject untrusted hook changes, and never execute requests directly from the dashboard; isolate the dashboard collector from the privileged runner, use authenticated and authorized requests with scoped credentials, rotation and audit, and do not treat a Tunnel or private network as authentication; unattended Backups introduce disk-full, overlapping-job, stale-credential, and restore-readiness risks, so publish last-success/age metrics, bound local spooling, verify archives and periodically test restoration, and avoid unattended production auto-updates by default.
