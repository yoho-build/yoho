# Design consult brief: Yoho (2026-10-08)

Read `GLOSSARY.md`, `docs/decisions.md`, `docs/adr/*.md`, `docs/backlog.md`, `docs/research/2026-10-08-landscape.md` first. Yoho is a Go CLI replacing Kamal + ONCE + Ansible, compose-native, deploying over SSH. No code exists yet. We want an opinionated design, not a survey. Be concrete (config shapes, command sequences, file paths on the Server). Flag risks to data, secrets, and production uptime.

## Q1. Roles and multiple Servers, forward-compatible with v1

v1: one Server per Destination, whole App on it. Later: Kamal-style Roles (subset of Services on subset of Servers), and maybe N identical web Servers.

- What must the v1 config shape and on-Server layout look like so Roles can be added later without breaking changes?
- Stateful Services (Postgres, Redis, volumes) are the trap: the same compose on 2 Servers creates 2 independent databases. How should Yoho model this? Options: mark Services `stateful`/`singleton` and pin them to one Server; require external DB; refuse multi-Server for Apps with named volumes unless pinned; cross-Server networking (WireGuard / Tailscale / private network) so web on Server B reaches DB on Server A.
- How do Roles map onto compose: compose `profiles`, generated per-Server override files, `docker compose up <services...>`, or something else? Cross-Server service discovery?
- Backups and restore when a stateful Service is pinned to one Server.

## Q2. Secrets: best end-to-end design

Requirements: providers 1Password CLI (`op`), Bitwarden (`bw`), Bitwarden Secrets Manager (`bws`), arbitrary command; build-time secrets (buildx `--secret`) and runtime secrets; Kamal-style `.yoho/secrets[.<destination>]` dotenv with `$(...)`; no plaintext secrets in repo or image; current user practice is plaintext `.env` copied 0644 (bad). Also: Backup archive passwords read from a password manager; scheduled jobs on the Server (backups at 3am) need secrets when the laptop is offline.

- Where do resolved runtime secrets live on the Server (0600 env file, tmpfs, compose `secrets:` files, docker secrets without swarm)? Survive reboot?
- How does a Server-side scheduled job get secrets without the laptop (machine tokens: 1Password service account, `bws` access token, stored on Server)? Trade-offs.
- Rotation, audit (which secret version deployed), redaction in logs, `yoho secrets print` safety.
- Compose interaction: `env_file`, interpolation `${VAR}` in compose, `secrets:` top-level.

## Q3. Server-side sidecar vs no daemon

ADR 0003 says no resident daemon by default. The user now proposes a sidecar container that runs scheduled tasks (backups, cron), later exposes an API for a remote dashboard (health, Server metrics, on-call alerts). The user said "one sidecar per service". Options: one sidecar per compose Service, one per App (inside the App's compose project), one per Server (system-level `yoho` container), or systemd timer running the `yoho` binary.

- Recommend one, and how it reconciles with ADR 0003 (opt-in?). Security: Docker socket access, API exposure (behind the Proxy / Tunnel / Tailscale only), auth.

Answer each Q with: recommendation, why, config sketch, risks. Under 1500 words total.
