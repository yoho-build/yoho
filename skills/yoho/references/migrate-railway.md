# Migrate from Railway

The site guide is the playbook: `docs/site/migrating-from-railway.md`, or https://yohobuild.com/migrating-from-railway/ . Read it before editing files. Railway is not on the Yoho Server. Do not invent Railway CLI flags. The pages cited in the guide were retrieved 2026-10-23.

The sample App is `examples/quickstart` (web, worker, Postgres). Names only, no values: `examples/quickstart/railway/inventory.json`.

1. Inventory names, never values. `railway variable list` prints values (https://docs.railway.com/cli); read names on screen and do not redirect it to a file. Create items in 1Password or Bitwarden. Volume backups and point-in-time recovery restore only inside Railway (https://docs.railway.com/guides/postgres-backups-restores).
2. Draft with `yoho migrate draft --from FILE`. FILE is a names-only inventory JSON (Yoho's format, not a Railway export) or one service's deprecated `railway.json` / `railway.toml`. `--service` (default `web`) and `--project` (default `app`) apply to the config-as-code file. `--out DIR` writes `compose.yaml` and `yoho.yml` only when those names do not exist. It does not write `.yoho/secrets`, call Railway, or contact a Server. It refuses secret values. It does not parse `.railway/railway.ts`.
3. Secrets are references: `APP_GREETING=$(op read op://Production/shop/APP_GREETING)` or `APP_GREETING=$(bw get password shop-greeting)`. Do not copy `DATABASE_URL` or `RAILWAY_*`. `POSTGRES_PASSWORD` is `x-yoho.generate` (`password32`); do not copy Railway's password. Web and worker still list it in `x-yoho.secrets`. `yoho config check --offline` does not run `$(...)`. `yoho secrets list` shows lengths.
4. First deploy has no `migrate` block. Use `examples/quickstart/yoho.yml` (Quick Tunnel, empty proxy hosts) so Railway keeps the hostname. `yoho setup --plan`, `yoho plan`, `yoho deploy`, `yoho app ps`. Postgres starts empty.
5. Freeze writes in the Railway dashboard. `railway scale` flags are not documented on the CLI page; do not invent them. Dump with the backup guide's commands: `railway connect postgres --tunnel-only` (substitute the service name; the example is `postgres`), then `pg_dump ... --format=custom --no-owner`. Do not save the printed password. Do not commit `*.dump`.
6. Restore over SSH, not through `yoho app exec` (it does not forward stdin):

   `ssh root@YOUR_SERVER 'docker compose -p yoho-shop-production exec -T db pg_restore -U postgres -d postgres --no-owner --exit-on-error --clean --if-exists' < backup.dump`

   The project name is `yoho-<app>-<destination>`. `--clean --if-exists` is pg_restore: the first deploy already ran `release_command`. Verify with `yoho app exec db -- psql -U postgres -d postgres -c 'SELECT count(*) FROM jobs'`. `release_command` runs again on the switch deploy and must be safe to repeat.
7. Rehearse on a second Destination with no `migrate` block, its own servers, a restored copy, and `proxy: {tunnel: null}` in the overlay so it does not join the live tunnel.
8. Switch only after the counts match. Put the drafted `migrate` block back. `from: compose` is a label (`coolify | dokploy | compose` only). `stop.containers` is `railway-<project>-<first public service>` and matches nothing on this Server, so there is no `claim`. Run `yoho migrate plan --cutover-allow-empty`, then `yoho deploy --skip-build --cutover-allow-empty`. `yoho apply` returns before the cutover when the plan has no changes. With `migrate.tunnel`, ingress moves to `http://yoho-proxy:80` after health. DNS without a tunnel is manual. A `done` journal does not switch again.
9. Leave Railway running. Roll back with `yoho rollback --cutover` (restores saved tunnel ingress; does not change DNS, volumes, or migrations). For DNS, point the record back yourself. `yoho migrate status` shows `rolled_back`. A later deploy with `--cutover-allow-empty` starts a new cutover. Do not run `railway down` until the App is verified; the CLI page describes it as removing the latest deployment.
